# Worker self-loop

Короткий **повторяющийся** чеклист для **worker**-pane. Оркестратор крутит свой луп ~3 мин; у воркера **другой ритм**, чтобы не рвать глубокую работу.

## Интервал

- **~6 минут** между запусками этого self-loop (таймер, напоминание или каждый N-й «тик» вручную).
- Если ты **в середине** tool-run / Thinking / длинного теста / глубокой реализации — **не прерывай**: закончни текущий атомарный шаг (заверши команду, дождись результата, выйди из компактного блока), **затем** прогони self-loop на ближайшем естественном паузе.
- Если же ты **стоишь у пустого prompt** или делаешь мелочь (bv, mail check, чтение файла) — self-loop срабатывает по таймеру штатно.
- Логика: **не интервал прерывает работу, а завершённый атомарный шаг запускает следующий loop**.

## Синтаксис скиллов по типу pane

| CLI | Префикс скилла |
| --- | --- |
| Claude Code (`cc`) | `/skill-name` |
| Gemini CLI (`gmi`) | `/skill-name` |
| Codex (`cod`) | `$skill-name` |

Во всех пунктах ниже **подставь** нужный префикс для своего pane.

## Процедура (вставь в CLI как «напоминание» или выполняй по шагам)

```text
/worker-self-loop   # опционально: свой shortcut / алиас; суть — шаги ниже

Ты worker. Сейчас self-loop (~12 мин). Сделай по порядку:
1. Перечитай этот файл `WorkerLoopPrompt.md`, блок «Запрет терминального простоя» в `RolePrompts.md` (worker), и **`RulesRefresh.md`** — **полный** refresh AGENTS/CLAUDE (проект + глобальный) **каждый self-loop (~12 min)**.
2. Agent Mail: inbox + reservations — новый marching-order? ack_required? overlap? Сначала Mail, потом новый work.
3. **Память (PAI + CM + ContextSearch) — recall перед сложным шагом:** если bead нетривиален — `cm context "<bead topic + project + симптом>" --json`; если нужен **исторический** контекст (незнакомая область, повторяющийся симптом, мало historySnippets) — literal `<prefix>context-search <topic>`; при застревании — `cass search "<symptom>" --json`. Не-очевидный урок → Edit PRD `## Decisions` или `/ce-compound`.
4. **Локальный поиск скилла (ms) — для нового или нетривиального bead:** прежде чем уйти в реализацию по интуиции, выполни `ms suggest --cwd <repo path>` и при необходимости `ms search "<bead topic>" --robot` — это ищет среди **уже установленных** локальных скиллов и часто выдаёт более точный workflow, чем твой текущий bundle. Если нашёл лучший скилл — вызови его буквально (`<prefix>skill-name`) и переключи подход; не блокируйся если ничего не нашлось — fallback в `SkillRouting.md`.
5. Текущий bead: если есть in_progress — есть ли реальный прогресс с прошлого self-loop? Нужно ли зарезервируемые пути обновить / отпустить?
6. Если у **пустого** prompt и нет активной задачи: `bv --robot-triage --format toon` и `bv --robot-next` — claim следующий ready или **одна** строка в Mail («worker свободен, inbox проверен, bv пуст/блокер»). Не стой без действия.
7. Если застрял — `/clear`, переформулируй, Mail при блокере. **Перед `/clear`** — Edit PRD `## Decisions` с симптомом если не банальный typo.
8. Напоминание: буквальные первые вызовы `<prefix>agent-mail`, `<prefix>cass-memory`, `<prefix>context-search` (если в marching order), `<prefix>ce-work`, … из marching order.
9. Продолжай текущий bead или только что взятый next — без «терминального простоя».
```
## Связь с оркестратором

Оркестратор **не заменяет** этот self-loop: он координирует рой. Ты **сам** каждые ~12 мин гарантируешь, что не завис в пустом состоянии и не пропустил Mail.

См. `Gotchas.md` → **Workers Must Not Park At Empty Prompt**, `OperatingProcedure.md` → **Worker Continuity**.
