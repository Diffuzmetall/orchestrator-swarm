# Codex (`cod`): критерийно-измеримая цель через `/goal`

В Codex команда постановки цели — **slash-команда `/goal`** (не `$goal`). Остальные вызовы скиллов из registry по-прежнему задаются префиксом **`$`** (`$agent-mail`, `$ce-work`, …) — см. `RolePrompts.md` и `Gotchas.md` → Skill Syntax Drift.

`/goal` фиксирует **конечное состояние** и **проверяемые критерии** до ухода в реализацию. Это близко к **Ideal State Criteria (ISC)** в PAI Algorithm — см. `ISC-style criteria in `GoalDispatch.md` → актуальная версия в `LATEST` (например `v3.7.0.md`: атомарные критерии, бинарная проверяемость, разбиение составных требований).

## Когда оркестратор обязан включать `/goal`

| Ситуация | `/goal` |
| --- | --- |
| Bead затрагивает **несколько файлов/подсистем**, интеграцию, контракты | **Да** |
| Acceptance **неочевиден** из одной строки `Goal:` в bead | **Да** |
| Риск «сделал объём работы, но не то» (QA, auth, API) | **Да** |
| Тривиальный one-file fix с явным критерием в bead | Можно **опустить** |

Если сомневаешься — **включи**: лишняя ясность дешевле, чем переделка.

## Порядок первых вызовов на `cod`

Сохраняй обязательный блок **буквальных строк** из `RolePrompts.md`. Типичная вставка **`/goal`**:

1. `$agent-mail` (и далее по orchestrator-списку для bootstrap).
2. **`/goal`** — с **полным телом** по шаблону ниже (один вызов с многострочным аргументом — как принято в твоём `cod`; если CLI принимает только одну строку, отправь компактный вариант + остальное в Agent Mail `body_md`).
3. Остальные строки: `$beads-bv`, `$ce-work`, … — как в dispatch.

Не заменяй `/goal` «Goals:» в prose — только **литеральная** команда **`/goal`**, иначе не считается вызовом.

## Шаблон тела для `/goal` (скопируй и заполни)

Соотнеси **Критерии готовности** с ISC: один пункт — **одна** независимо проверяемая вещь (без «и ещё» в одном буллете).

```text
Цель: <конечный результат одной фразой — что будет истинно в мире, когда bead закрыт>

Контекст:
- Проект/репозиторий: <абсолютный или нормализованный путь>
- Bead: <BD-ID>
- Текущая проблема/задача: <что не так сейчас / что меняем>

Критерии готовности (бинарно проверяемые):
- [ ] <критерий 1 — как доказать PASS/FAIL>
- [ ] <критерий 2>
- [ ] <критерий 3>

Ограничения:
- Стек / инструменты: <что использовать>
- Не делать: <anti-goals, out of scope — как ISC-A в Algorithm>
- Лимит по времени/изменениям: <например «только файлы X,Y» / «без рефакторинга вне задачи»>

Формат результата:
- Что должно быть изменено/создано: <файлы, артефакты, поведение>
- Как проверить, что цель достигнута: <команды тестов, ручная проверка, curl, сценарий>
```
## Опционально: TDD-формат критериев

Если bead требует явного тест-покрытия или acceptance формулируется через тесты — замени раздел «Критерии готовности» на TDD-формат (запускается в связке с `$tdd` / `/tdd`):

```text
Критерии готовности (TDD-формат):
- [ ] Тест "should <expected behaviour> when <condition>" — GREEN
- [ ] Тест "should reject <invalid input>" — GREEN
- [ ] Регрессионный тест для бага <описание> — GREEN
```
**Когда применять:** bead — new feature с чётким поведенческим контрактом, bugfix с воспроизводимым симптомом, или ревьювер явно просит TDD-покрытие. Для тривиальных правок оставляй свободный формат из основного шаблона.

## Связка с Beads

- В **`Контекст`** и **`Критерии`** дублируй смысл bead, но **раскладывай** составной bead на атомарные буллеты (как **Splitting Test** в Algorithm).
- Закрытие bead (`br close`) — только когда **все** релевантные пункты из **`/goal`** выполнены или перенесены в новый bead осознанно.

## Оркестратор: где это жить

- Краткое правило: `SKILL.md` (Mandatory Constraints), детали: этот файл + `RolePrompts.md` → Worker для `cod`.
